# DRY judgment contrasts

## Shared knowledge

Two authentication handlers each independently calculate the same token lifetime from the same policy constant and unit conversion. When supplied context establishes both implement that policy, consolidate its representation or reference the existing owner. Cite the duplicate operation, not the entire handler.

## Independent policies

Invoice retention and access-token expiry both currently equal thirty days. Matching numbers and arithmetic do not establish one policy owner. Keep independent domain names and responsibilities even if a detector marks them as clones.

## Test scenarios

Two tests each visibly supply an expired token and assert their own expected denial. Do not hide these inputs or expectations in an assertion helper. A repeated multi-step server setup can be a cohesive scenario fixture when its shared responsibility is visible.

## External representation

The same required field name appears in a server protocol schema and its client fixture. The external contract may require both representations. Without evidence that the repository owns a shared generation/definition mechanism, this is not a DRY violation.

## Wrong abstraction

Two operations differ in lifecycle and responsibilities. A proposed shared helper needs unrelated boolean switches and conditional branches to support both. Similar implementation shape does not justify that extraction.
